# Instructions de travail pour Codex

## Contexte
Je suis en formation de développeur web et web mobile.
Ce projet "Vite & Gourmand" est un projet d'évaluation.

## Méthode de travail
- Avancer étape par étape.
- Ne pas modifier plusieurs fonctionnalités en même temps.
- Expliquer ce qui va être fait avant toute modification importante.
- Privilégier des explications adaptées à un développeur débutant.
- Me laisser comprendre et valider chaque étape avant de poursuivre.
- Ne pas complexifier inutilement le code.
- Préférer des solutions simples, lisibles et faciles à expliquer à un jury.
- Lorsqu'une tâche comporte plusieurs étapes, présenter brièvement le plan général,
  puis ne détailler que la prochaine étape à réaliser.
- Attendre ma validation avant de passer à l'étape suivante.

## Modifications du code
- Ne pas modifier un fichier si je demande uniquement une analyse ou une explication.
- Avant une modification importante, indiquer quels fichiers seront concernés et pourquoi.
- Éviter les refactorisations globales non demandées.
- Conserver la structure existante du projet lorsque c'est pertinent.
- Ajouter des commentaires uniquement lorsqu'ils apportent une vraie aide à la compréhension.

## Qualité
- Respecter HTML, CSS, JavaScript et PHP standards.
- Conserver une indentation et une mise en forme cohérentes.
- Signaler les erreurs ou mauvaises pratiques sans forcément les corriger immédiatement.
- Expliquer les choix techniques proposés.

## Git
- Les messages de commit doivent être rédigés en français.
- Ne pas effectuer de commit ou de push sans demande explicite.

## Énoncé de l'évaluation

- Le fichier `docs/enonce.pdf` contient l'énoncé officiel de l'évaluation.
- Cet énoncé constitue la référence pour les fonctionnalités et contraintes obligatoires du projet.
- Avant de proposer une fonctionnalité importante, vérifier qu'elle respecte les exigences de l'énoncé.
- Ne pas inventer une exigence qui n'est pas présente dans l'énoncé.
- Distinguer clairement ce qui est obligatoire dans l'énoncé de ce qui constitue une proposition ou une amélioration facultative.
- Si une décision technique s'écarte de l'exemple fourni dans l'énoncé, expliquer pourquoi ce choix reste compatible avec les exigences de l'évaluation.

## Maintenance de la documentation

La documentation située dans le dossier `docs/` fait partie du projet et doit rester cohérente avec son état réel.

Lorsqu'une étape de développement entraîne :
- une nouvelle décision technique ;
- un changement de technologie ;
- une évolution importante de l'architecture ;
- l'achèvement d'une fonctionnalité ;
- ou l'apprentissage d'une notion importante ;

signaler qu'une mise à jour de la documentation peut être nécessaire.

Indiquer quel document devrait être mis à jour et expliquer brièvement pourquoi.

Ne pas modifier automatiquement la documentation sans ma validation.

Documents concernés notamment :
- `docs/avancement.md` : état actuel du développement ;
- `docs/choix-techniques.md` : décisions techniques et leurs justifications ;
- `docs/notions.md` : notions importantes apprises pendant le développement.
